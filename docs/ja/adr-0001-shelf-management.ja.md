# ADR-0001: 棚の編集機能を url-shelf 内に持つ（実装後に撤回）

> Date: 2026-07-26
> Status: **Reversed**（同日: 実装 → 撤回）

## 背景

RFP の時点では、url-shelf は「読んで開く」だけの道具だった。棚の再編成は Finder で
行う前提で、それはツールにロックインされないという設計思想の帰結でもあった。

実際に `.webloc` 群を棚として使うと、Finder では埋まらない穴が見えた。

| 操作 | Finder | 評価 |
|---|---|---|
| フォルダの作成・リネーム・移動・削除 | できる | アプリ内で完結すると便利、という程度 |
| webloc の移動・削除 | できる | 同上 |
| **エントリの URL / 開き方 / ブラウザ指定の編集** | **できない**（plist の手編集が必要） | **本質的な穴** |
| 並び順プレフィックスの維持 | できるが手作業 | 苦痛 |

## 当初の決定

Shelf ウィンドウ（ツリー＋インスペクタの 2 ペイン）を追加し、リネーム・移動・削除・
メタデータ編集・ドラッグでの並べ替えを提供する。削除はゴミ箱経由、リネームは並び順
プレフィックスを保存、並べ替えはフォルダ単位でファイル名を採番し直す。

## 撤回

**実装したが、操作感が要求水準に達しなかったため機能ごと削除した。**

行き詰まったのは SwiftUI のツリーにおけるドラッグ&ドロップである。

1. `.dropDestination` はドロップ確定時にしかポインタ位置を返さない。挿入位置を示す線が
   出せず、離すまでどこに入るか分からない操作になった
2. `DropDelegate` に切り替えると位置は取れるが、今度はセッション終了の通知が信用できない。
   `dropExited` も `performDrop` も必ず来るとは限らず、ドロップ後に `dropUpdated` が
   余分に届く経路もある。結果として挿入線が消えずに残った
3. クリア箇所を増やしても取りこぼしが残り、最終的に「更新が途絶えたら消す」という
   ウォッチドッグに退避した。動くが、タイマーで UI の状態を推測している時点で筋が悪い
4. 加えて、ビューのボディから毎回ツリーを走査していたためドラッグ中に事実上フリーズした
   （キャッシュで解消したが、SwiftUI のツリー＋D&D という組み合わせの当たりの悪さが露呈した）

**この道を続けるなら `NSOutlineView`（AppKit）で書き直すのが筋**だが、その規模の投資に
見合う機能ではないと判断した。棚の再編成は Finder が最初から得意であり、url-shelf の
存在理由は「開くこと」であって「ファイルを管理すること」ではない。

## 撤回後の状態

- Shelf ウィンドウ、ツリー、インスペクタ、ドラッグ&ドロップ、並べ替え、ゴミ箱削除を削除
- フォルダの作成・リネーム・移動・削除、webloc の移動・削除は **Finder で行う**
- 新規エントリの開き方・ブラウザ指定は **Add URL ウィンドウ**で指定できる
- **既存エントリのメタデータをアプリ内から変更する手段は無い**。`.webloc` の plist を
  手で編集するか、追加し直す。これが撤回で失った唯一の実質的な機能である
- 並び順は従来どおりファイル名の数字プレフィックス。Finder でリネームして調整する

## 学び

- SwiftUI の `List` / `OutlineGroup` の上で、ドラッグ&ドロップの**セッション終了を正確に
  扱うのは現実的でない**。挿入インジケータを伴う並べ替えが要るなら最初から `NSOutlineView`
  を使う
- ビューのボディからファイルシステムを走査しない。SwiftUI はボディを高頻度で再評価する
- 「Finder でできること」をアプリに再実装する前に、それが本当に必要かを問う。今回本当に
  必要だったのは**メタデータ編集だけ**で、ファイル操作はその巻き添えで入っていた。
  再挑戦するなら、ツリーを持たずエントリ 1 件を編集する小さなウィンドウから始めるべき
